# گزارش فاز A — تحلیل و ثبت خط مبنای UI/UX و دارایی‌های Hexara

تاریخ: ۳۰ ژوئیهٔ ۲۰۲۶  
مبنای بررسی: commit `77044c5` روی شاخهٔ `master`  
دامنهٔ این فاز: فقط تحلیل، فهرست‌برداری، ثبت تصاویر و پیشنهاد مسیر؛ بدون تغییر کد محصول، منطق بازی، API، SignalR یا مدل داده.

## نتیجهٔ اجرایی

Hexara از نظر زیرساخت رابط وضعیت خوبی دارد: Vue 3 و TypeScript به‌صورت island داخل ASP.NET Core اجرا می‌شوند، صحنهٔ بازی داده‌محور است، دارایی‌ها رجیستری مرکزی و fallback دارند، و طراحی برای تم روشن/تیره، RTL/LTR، safe-area و reduced-motion از قبل پایه‌گذاری شده است. بنابراین بازطراحی باید یک «ارتقای کنترل‌شده» باشد، نه بازنویسی.

بزرگ‌ترین شکاف‌ها:

1. کیفیت بصری زمین‌ها، مهره‌ها و بندرها هنوز با هدف تصویر مرجع فاصله دارد و بیشتر روی رنگ‌های تخت و هندسهٔ اولیه متکی است.
2. دوربین بورد با نسبت تصویر تطبیق کامل ندارد؛ در لپ‌تاپ، تبلت و موبایل بخش مهمی از نقشه بریده می‌شود.
3. هدر فارسی در موبایل حدود `622px` عرض محتوا تولید می‌کند، درحالی‌که عرض واقعی viewport آزمایش‌شده `375px` است؛ بعضی اکشن‌ها خارج صفحه می‌روند.
4. شیت موبایل فقط دو حالت باز/بسته دارد و در حالت باز تا `60dvh` از صفحه را می‌پوشاند؛ حالت نیمه‌باز/تمام‌صفحه و حرکت drag ندارد.
5. حلقهٔ رندر Three.js همیشه در حال اجراست و chunk مربوط به Three حدود `510.21 kB` است؛ پیش از افزودن بافت و افکت باید بودجهٔ عملکرد تعیین شود.

| موضوع | وضعیت فعلی | پیام برای بازطراحی |
|---|---|---|
| پوستهٔ وب | ASP.NET Core 10 MVC/Razor | مسیرها و رفتار server-rendered حفظ شود |
| رابط تعاملی | Vue 3 + TypeScript + Vite، با islandهای lazy | تغییرات باید در islandهای موجود متمرکز بماند |
| صفحهٔ بازی | `GameLive.vue` متصل به SignalR و `GameView` واقعی | mock یا جایگزینی قرارداد سرور مجاز نیست |
| بورد | Three.js r180، `GameBoard.vue` و `three/board.ts` | صحنه را توسعه می‌دهیم، نه اینکه با تصویر تخت جایگزین کنیم |
| دادهٔ بورد | `BoardData` شامل tiles، ports، buildings، roads و robber | تعداد/چیدمان hexها hardcode نشود |
| زمین | CylinderGeometry رنگی + scenery رویه‌ای و deterministic | بافت/تنوع اضافه شود، اما از داده جدا و تکرارپذیر بماند |
| توکن عدد | CanvasTexture مستقل برای هر مقدار؛ ۶ و ۸ قرمز و pipدار | استقلال توکن از زمین حفظ شود |
| مهره‌ها | آبجکت‌های مستقل Three.js و چند SVG دوبعدی | سیلوئت و جزئیات قابل ارتقاست؛ قرارداد بازی دست‌نخورده بماند |
| دارایی‌ها | `assets/registry.ts`، `Asset.vue`، fallback و تست رجیستری | رجیستری موجود گسترش پیدا کند؛ مسیر پراکنده ایجاد نشود |
| طراحی | `tokens.css`، `app.css` و `docs/design-system.md` | توکن‌های موجود منبع اصلی باشند و تکمیل شوند |
| ریسپانسیو | desktop rail، mobile bottom sheet و حالت landscape | دوربین و رفتار شیت نیازمند بازطراحی اصلی است |
| قابلیت‌های ارتباطی | چت/صدا/ویدئو و LiveKit/WebRTC وجود ندارد؛ سیاست امنیتی camera/microphone را می‌بندد | بدون دامنه و backend صریح، UI نمایشی برای قابلیت غیرواقعی ساخته نشود |
| feature flag | چارچوب frontend برای feature flag پیدا نشد | قابلیت‌های پرریسک باید با سازوکار کوچک و مستند اضافه شوند |

## فهرست دارایی‌های فعلی

در `ClientApp/src/assets/svg` تعداد ۲۷ فایل SVG مستقل وجود دارد؛ مجموع اندازهٔ آن‌ها حدود `23.5 kB` است و Vite به‌دلیل اندازهٔ کمتر از ۴ کیلوبایت اغلب آن‌ها را inline می‌کند.

| خانواده | دارایی‌های موجود | ارزیابی |
|---|---|---|
| منابع | lumber، brick، grain، wool، ore | ساختار و نام‌گذاری قابل حفظ؛ تصویرسازی و قاب نیازمند ارتقا |
| کارت توسعه | knight، victory point، road building، year of plenty، monopoly، card back | پوشش پایه خوب؛ سبک فعلی تخت و جزئیات محدود |
| مهره | road، settlement، city، robber | برای fallback مناسب؛ برای هدف نهایی کم‌جزئیات |
| بندر | generic و پنج منبع | پوشش داده‌ای خوب؛ نمایش سه‌بعدی فعلی ابتدایی |
| آیکن | bank، cards، dice، trade، victory point | ناکافی برای همهٔ وضعیت‌ها و اکشن‌های رابط |
| آواتار | placeholder | قابل حفظ به‌عنوان fallback |

### دارایی‌های مفقود یا ناکافی

- شش خانوادهٔ زمین با چند variation کنترل‌شده، ساحل/دریا و transitionهای لازم
- توکن‌های عدد ۲ تا ۱۲ در حالت‌های عادی، مهم و disabled، در صورت انتقال از CanvasTexture
- شش وجه تاس و فریم‌های محدود انیمیشن در صورت انتخاب راه bitmap
- ghostهای placement و حالت‌های valid، invalid، hover و selected
- پشت کارت منابع و حالت‌های placeholder/skeleton
- آیکن‌های پایان نوبت، ساخت، بازیکنان، تایمر، تنظیمات، صدا، ویدئو، چت، reconnect
- آیکن‌های accept، reject، counter، cancel، warning، success، error و info
- نشان‌های trophy، crown، longest road، largest army و وضعیت بازیکن

### تصمیم پیشنهادی

- **حفظ و توسعه:** رجیستری، `Asset.vue`، ساختار پوشه‌ها، fallbackها، قراردادهای alt/label، توکن‌ها، بارگذاری lazy.
- **بازسازی بصری:** زمین‌ها، بندرها، منابع، کارت‌های توسعه، مهره‌ها و آیکن‌های عملیاتی.
- **افزودن:** manifest دارایی‌های جدید، variation metadata، وضعیت‌های تعاملی و provenance/license.
- **حذف نشود:** هیچ دارایی فعلی تا زمانی که جایگزین ثبت‌شده و تست‌شده ندارد حذف نشود.

## ممیزی UI/UX واقعی

### دسکتاپ و لپ‌تاپ

- در `1920×1080` قاب اصلی پایدار است، ولی نقشه در پایین نزدیک به برش است و پنل راست به اسکرول داخلی طولانی متکی است.
- در `1366×768` ارتفاع سند به `882px` می‌رسد؛ پایین نقشه بریده می‌شود و rail راست `368px` از عرض را ثابت مصرف می‌کند.
- سلسله‌مراتب رنگی و قاب طلایی منسجم است، اما بورد نسبت به پنل‌ها کیفیت تصویری و عمق کافی ندارد.

### تبلت و موبایل

- در `820×1180` عرض بورد `757px` است ولی قاب دوربین بخش بزرگی از نقشه را خارج نما نگه می‌دارد.
- در `390×844` عرض واقعی محتوا `622px` اندازه‌گیری شد؛ منشأ اصلی overflow، هدر و `hx-header__actions` است.
- شیت دست بازیکن در موبایل اطلاعات را نشان می‌دهد، اما همان rail کامل را در یک لایهٔ `60dvh` قرار می‌دهد و اولویت‌بندی محتوایی محدودی دارد.
- در landscape با `844×390` بورد بهتر جا می‌شود، ولی ارتفاع سند `520px` است و ترکیب بورد/rail هنوز کاملاً viewport-fit نیست.

### تم، زبان و دسترس‌پذیری

- تم روشن و تیره هر دو فعال و قابل استفاده‌اند.
- جهت فارسی RTL و انگلیسی LTR درست تغییر می‌کند؛ در LTR لپ‌تاپ overflow افقی دیده نشد.
- reduced-motion، اندازهٔ هدف لمسی برای coarse pointer و safe-area در CSS موجود است.
- رنگ بازیکن تا حدی با شکل مهره همراه است، اما برای roadها و بعضی وضعیت‌ها هنوز نباید تنها نشانهٔ تمایز باشد.

### مشکلات با اولویت

| اولویت | مسئله | اثر |
|---|---|---|
| بحرانی برای بازطراحی | fit دوربین در نسبت‌های portrait و کوتاه | بخشی از وضعیت بازی دیده نمی‌شود |
| زیاد | overflow هدر فارسی در موبایل | اکشن‌های اصلی خارج viewport می‌روند |
| زیاد | شیت موبایل بدون حالت نیمه‌باز/تمام‌صفحه | نقشه و اطلاعات هم‌زمان قابل استفاده نیستند |
| زیاد | نبود variation و بافت منسجم برای زمین | بورد مهم‌ترین نقطهٔ رابط است ولی حس موقت دارد |
| متوسط | rail طولانی و اسکرول چندلایه | اسکن اطلاعات کند و کنترل نوبت دور از دسترس می‌شود |
| متوسط | حلقهٔ رندر دائمی و chunk بزرگ Three | افزودن افکت می‌تواند مصرف باتری/GPU را بالا ببرد |
| متوسط | پوشش کم آیکن‌ها و وضعیت‌ها | تکیه بر متن و نشانه‌های ناهماهنگ |
| کم | پورت‌های شناور و هندسهٔ ساده | خوانایی هست، اما کیفیت هدف را ندارد |

## نکات فنی و ریسک‌ها

- scenery فعلی با مختصات axial deterministic است؛ این مزیت باید حفظ شود. اگر variation تصویری اضافه شود، انتخاب آن از seed پایدار انجام شود، نه `Math.random()`.
- `GameBoard.resize()` اندازه و aspect را عوض می‌کند، ولی فاصله/هدف دوربین را برای نسبت جدید fit نمی‌کند؛ این علت اصلی برش در portrait است.
- renderer روی دستگاه‌های ضعیف DPR و کیفیت را کاهش می‌دهد که تصمیم خوبی است؛ بافت‌ها باید atlas، فشرده و دارای سقف رزولوشن باشند.
- صحنه حلقهٔ `requestAnimationFrame` مداوم دارد. رندر on-demand یا pause در tab مخفی باید در فاز عملکرد بررسی شود.
- قراردادهای `BoardData` و SignalR مرز سخت‌اند. تغییر بصری نباید ترتیب رویدادها، hit-test، placement یا trade را عوض کند.
- افزودن چت/صدا/ویدئو نیازمند تصمیم محصول، سرویس، مجوز مرورگر، backend و سیاست امنیتی است؛ در این پروژه فعلاً صرفاً «شکاف قابلیت» ثبت شده است.

## نتایج build و test خط مبنا

- `dotnet build Hexara.slnx -c Release --no-restore`: موفق، بدون warning و error.
- `npm run build`: موفق؛ هشدار بودجه برای chunk سه‌بعدی `510.21 kB`.
- `npm test`: هر ۸۳ تست frontend در ۶ فایل موفق.
- suiteهای .NET به‌صورت جداگانه و سریالی اجرا و موفق شدند: Domain تعداد ۲۳۹، Application تعداد ۱۸۶ و Web تعداد ۱۰۵ تست؛ در مجموع ۵۳۰ تست، بدون شکست یا skip. تست یک‌جای solution در اجرای اولیه پس از حدود ۱۵ دقیقه بدون گزارش مفید exit code 1 داد و برای تفکیک علت به suiteهای مستقل شکسته شد.
- کنسول مرورگر در جریان سناریوی واقعی دو بازیکن، شروع بازی، تغییر زبان و تم، error یا warning ثبت نکرد.

## مسیر پیشنهادی فازهای بعد

### فاز B — پایهٔ طراحی و رجیستری

- تکمیل توکن‌ها و قواعد responsive بدون شکستن design system فعلی
- تعریف budget برای تصویر، GPU و bundle
- گسترش رجیستری با variation، state و provenance
- ساخت پوستهٔ responsive جدید پشت feature flag یا مسیر بازگشت روشن

### فاز C — تولید دارایی

- تولید یک vertical slice مستقل برای یک زمین، توکن، منبع، مهره و آیکن
- بررسی کیفیت در تم روشن/تیره و در مقیاس واقعی بورد
- سپس توسعهٔ خانواده‌ها با naming و manifest ثابت

### فاز D — ادغام بورد

- اصلاح fit دوربین، portrait framing و placement overlay
- بارگذاری lazy، cache و fallback
- حفظ استقلال terrain/token/piece و قرارداد `BoardData`

### فاز E — پنل‌ها و ریسپانسیو

- رفع overflow هدر
- rail اولویت‌بندی‌شده در desktop
- bottom sheet سه‌حالته در mobile و کنترل‌های مناسب لمس

### فاز F — عملکرد و دسترس‌پذیری

- اندازه‌گیری FPS، memory، draw calls و bundle
- pause/on-demand render، texture compression و keyboard/focus audit
- کنترل contrast، motion و تمایز غیررنگی بازیکنان

### فاز G — QA نهایی

- سناریوی چندبازیکن واقعی، reconnect، trade و placement
- ماتریس RTL/LTR، light/dark، desktop/tablet/mobile
- بررسی visual regression و به‌روزرسانی مستندات

## معیار تأیید برای ورود به فاز B

پیشنهاد این است که فاز B فقط پس از تأیید این سه تصمیم آغاز شود:

1. سبک هدف: تصویرسازی stylized با عمق و بافت کنترل‌شده، نه فوتورئال و نه کپی از بازی مرجع.
2. اولویت اجرایی: ابتدا fit دوربین و پوستهٔ responsive، هم‌زمان با vertical slice دارایی؛ سپس تولید انبوه دارایی.
3. قابلیت‌های چت/صدا/ویدئو خارج از دامنهٔ فعلی بمانند مگر اینکه قرارداد backend و سرویس آن‌ها جداگانه تأیید شود.
